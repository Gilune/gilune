# LAN sync: discovery, pairing, transport — research note

Researcher's report for the M5 design round, 2026-09-02. Primary sources
cited inline. Anything I could not put against a primary source is marked
**UNVERIFIED**; vendor self-description is called out as such. Repo facts
carry file and line references. Recommendations are confined to § 7 —
the decision itself is ADR 0019.

The owner's fixed constraints for this round (2026-09-02, not reopened
here): M5 is transport only, full applications, no headless agent; every
device is a **full replica** (whole op history, all blobs); the phone
syncs on open/foreground plus a periodic Wi-Fi background job; the
desktop is an always-available listener; pairing is a 6-digit short code
**and** a QR path, both in v0; per-device long-lived identity keys;
encrypted transport from a boring well-reviewed Rust library; revocation
from either side; a device restored from backup re-enrols as a new
identity.

---

## 0. The starting position in the tree

**The production kernel writes operations and has never read one.**

- Schema version 4 (`kernel/crates/gilune-kernel/src/store.rs:13`). The
  `operations` table (`store.rs:241-250`) carries `op_id`, `device_id`,
  `op_seq`, `kind`, `target_id`, `payload`, `created_ms`, unique on
  `(device_id, op_seq)`. **No parents, no frontier, no integrity field,
  no raw-envelope column.**
- `record_operation` (`capture.rs:212-238`) is `pub(crate)`; four kinds
  are written (`create-source`, `create-revision`, `create-object`,
  `tombstone`). Nothing reads them but `COUNT(*)`.
- There is **no apply path, no frontier table, no device table, and no
  key material anywhere in `kernel/`**. A grep for
  `private_key|keypair|signature|encrypt` over `kernel\crates` returns
  nothing.
- `op_seq` is a **single global counter** in `meta`, not per-device
  (`capture.rs:212-238`). Correct while the kernel only ever writes its
  own ops; wrong the moment remote rows are inserted.
- `revisions::add_revision` **deletes every existing head** before
  inserting the new one (`revisions.rs:65`). The production kernel has
  no multi-head representation at all; the spike does
  (`spikes/s2-durable-capture/src/sync.rs:362-371`, `supersedes`-driven
  selective deletion).
- `device_id` is a bare UUIDv7 in `meta`, minted at store open
  (`store.rs:47-50`, `ids.rs:5-7`), **inside the vault**. Copy a vault,
  copy the identity and its sequence space.
- No size bound exists on any path. `CHUNK_BYTES = 64 * 1024`
  (`external.rs:31`) is a read buffer, not a cap.
- The kernel has **no alert surface** — migrations v1–v4 carry no such
  table — so the spike's visible `sync-gap` / `sync-corrupt-operation`
  signals have nowhere to land today.

**The S4 spike is where the semantics live.** Its `sync.rs` splits
cleanly: `apply_operation`, the frontier arithmetic, the gap and
corrupt-op halt policy, the `supersedes` head rule, unknown-kind
preservation and the origin-device processing policy are all
transport-blind; only path construction, `write_immutable`, directory
enumeration and `{seq:012}.json` naming are relay-specific. Its
`sync_frontiers(device_id PRIMARY KEY, applied_seq)` table
(`spikes/s2-durable-capture/src/store.rs:206-209`) is the shape a
production frontier needs.

One spike defect is load-bearing for a hostile transport:
`assemble_pending_blobs` does `Vec::with_capacity(byte_len)` from an
**attacker-supplied manifest** (`sync.rs:432`). Over a folder that is a
trusted local file; over a socket it is a one-packet OOM.

**Nothing networking, crypto, mDNS, QR or camera is vendored anywhere** —
not in `kernel/`, not in the spikes, not in Gradle. `sha2` is the only
cryptographic primitive present and it is used for integrity only.
Android currently declares `RECORD_AUDIO`, `FOREGROUND_SERVICE`,
`FOREGROUND_SERVICE_MICROPHONE`, `POST_NOTIFICATIONS`, `INTERNET`,
`ACCESS_NETWORK_STATE` and nothing else; `minSdk = 29`,
`targetSdk = 36`, `abiFilters = arm64-v8a, x86_64`
(`app/composeApp/build.gradle.kts:141`).

Two constraints bind every option below:

- **`Rust does not call platform APIs directly except through registered
  capability adapters`** (`architecture/decisions/0001-...md:95-96`).
- **Kernel contribution under 15 MB per ABI**
  (`architecture/spikes/README.md:36`), now joined by a companion
  app-package budget (ADR 0001 Amendments, 2026-09-02) so bytes moved
  across the FFI cannot be booked as a saving.

And one budget that is already written down and easy to miss:
**"LAN sync of 100 small operations between two idle devices: under
5 s"** (`architecture/spikes/README.md:37`). It predates this round and
it is a measurable acceptance number, not an aspiration — worth noting
that "idle devices" makes it a *discovery-plus-handshake-plus-exchange*
figure, so a cold mDNS browse is inside the 5 s, which is a further
argument for trying a cached address first (§ 1.4).

## 1. Discovery

### 1.1 mDNS/DNS-SD, Rust side

[`mdns-sd`](https://crates.io/api/v1/crates/mdns-sd) — **0.21.1,
released 2026-08-31**, `Apache-2.0 OR MIT`, 4.70 M total / 1.98 M recent
downloads, repo [keepsimple1/mdns-sd](https://github.com/keepsimple1/mdns-sd).
Safe Rust, small dependency set, **no async runtime dependency** — it
runs a daemon thread and talks over a flume channel, so it works from
sync code and from a future headless host with no executor. Responder
*and* querier in one crate. Its own README calls it "beta software
focusing on common use cases", tested against Avahi, macOS `dns-sd` and
Bonjour.

**Windows coexistence is the open risk.** Windows 10+ ships its own
mDNS responder bound to UDP 5353. Whether `mdns-sd` binds alongside it
cleanly on Windows 11 is **UNVERIFIED** — the crate's compatibility
testing names Avahi/macOS/iOS, not Windows. This is a measurement, not a
blocker: it is one afternoon at the start of the discovery stage, and
the fallbacks in § 1.4 make a negative result survivable rather than
fatal.

### 1.2 Android reality

Two mutually exclusive routes, and the difference is not stylistic.

**`NsdManager`** ([Android docs](https://developer.android.com/develop/connectivity/wifi/use-nsd))
is the platform's own DNS-SD service: register, discover, resolve. The
system holds the multicast socket, so the app needs **no multicast lock
and no `CHANGE_WIFI_MULTICAST_STATE`**. `NEARBY_WIFI_DEVICES` is not
required for mDNS over an already-joined Wi-Fi network — that permission
governs Wi-Fi Aware / Wi-Fi Direct / soft-AP APIs. Documented
constraints: service names must be unique and Android resolves conflicts
itself; ports must not be hard-coded but taken from the next available
and published; service types should follow `_<protocol>._<transport>`.
The docs surface I read lists no API-34/36-specific behaviour change —
**UNVERIFIED** that none exists.

**An in-process mDNS stack** (Rust `mdns-sd`, or JmDNS on the JVM) opens
its own multicast socket, and Android **disables multicast delivery by
default to save battery**: an app must hold a
[`WifiManager.MulticastLock`](https://developer.android.com/reference/android/net/wifi/WifiManager.MulticastLock)
and declare `CHANGE_WIFI_MULTICAST_STATE`. Every JmDNS-on-Android
recipe in the wild acquires one. That is a battery cost, a new
permission, and a lock whose behaviour with the screen off is exactly
what the platform is trying to suppress.

Historical note, second-hand: wrapper libraries such as RxBonjour
carried a JmDNS backend explicitly because of "the unreliable state of
the `NsdManager` APIs and known bugs" — a statement about older Android
versions, cited from a library README, **UNVERIFIED** against API 29–36.

### 1.3 Custom UDP broadcast

No library, no ecosystem, and it buys nothing. It needs the same inbound
firewall permission (§ 1.5), the same Android multicast lock (broadcast
is subject to the same suppression), and it would hand-roll name
conflict resolution, TXT-record-equivalent metadata and IPv6 that DNS-SD
already specifies. It also forfeits `NsdManager`: the one route that
makes Android discovery free is the one that only speaks DNS-SD.

### 1.4 When discovery fails

Discovery fails routinely and for reasons the app cannot fix: AP client
isolation (guest and many hotel/office networks), multicast filtering on
the AP, VLAN separation of the 2.4 and 5 GHz SSIDs, and a Windows
firewall that never got its rule (§ 1.5). Three layers answer it:

1. **Cached address first.** A paired peer's last-known `IP:port` is
   stored at pairing and refreshed on every successful session; a
   direct unicast connect is tried before any multicast is sent. This
   also makes the phone's background job cheap, since a background
   mDNS browse is the part most likely to be throttled or filtered
   with the screen off.
2. **Manual address entry.** The desktop shows its addresses and port
   in Settings; the phone can be told `host:port` directly. The QR
   already carries this, so the QR path works on a network where
   discovery does not.
3. **A named diagnostic.** "No device found" must be able to say
   *this network may not allow devices to talk to each other* rather
   than spinning, because on an isolated AP no amount of waiting
   helps.

### 1.5 The Windows firewall, honestly

Windows shows its Security Alert **when a program binds a local port to
listen for unsolicited inbound traffic**; a member of the Administrators
group can allow it from the dialog, and a non-administrator is merely
told the program was blocked
([Microsoft, firewall notification behaviour](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-server-2003/cc759451\(v=ws.10\));
the statement is from an older Windows Server document — that the
behaviour is unchanged on Windows 11 is **UNVERIFIED** by direct test).
Security event 861 records the same fact.

**No discovery mechanism dodges it.** mDNS needs an inbound UDP 5353
bind and the sync listener needs an inbound TCP bind, so mDNS is not a
way round the prompt; it is a second instance of it.

The relevant repo fact: ADR 0016 ships a **per-user MSI**, and
"normal installation and update do not require administrator elevation"
(`0016-...md:83-84`). So there is **no elevated installer moment in
which to pre-create a firewall rule**. What is left is shaping the
prompt rather than avoiding it: bind lazily at the moment the user turns
sync on (so a user who never syncs never sees it), explain it
immediately before it appears, keep the Private profile and leave Public
unchecked, and document the `netsh advfirewall firewall add rule …`
line for the non-administrator case.

## 2. Pairing and transport crypto

### 2.1 Why a PAKE is required at all, not merely chosen

Six digits is about 20 bits. Used as a Noise pre-shared key, one
captured handshake is enough to brute-force it offline in seconds. A
PAKE is the mechanism that makes a low-entropy secret survive: guesses
cost one *online* attempt each, and a wrong guess yields nothing to
grind on. That is the whole reason the short-code path needs one; the QR
path does not (its secret is long), but running both over one protocol
is cheaper than maintaining two.

### 2.2 SPAKE2

[`spake2`](https://crates.io/api/v1/crates/spake2) (RustCrypto/PAKEs) —
**stable 0.4.0 (2023-07-28)**, `0.5.0-pre.0` (2026-01-25),
`MIT OR Apache-2.0`, 1.22 M total downloads, MSRV 1.85.

Maintenance is honest but mixed: the repository is active (dependabot
runs, a pre-release cut in 2026), yet the stable release is three years
old. The project states plainly that the crate **"has never received an
independent third party audit"** and that no effort has been made toward
blinding or zeroising secrets
([RustCrypto/PAKEs](https://github.com/RustCrypto/PAKEs/tree/master/spake2)).

Its production evidence is the strongest available in Rust:
**magic-wormhole.rs depends on `spake2 = "0.4.0"`** — verified in the
[workspace `Cargo.toml`](https://raw.githubusercontent.com/magic-wormhole/magic-wormhole.rs/main/Cargo.toml) —
for exactly this problem (a short human-transferable code bootstrapping
a strong key). The same manifest carries `noise-protocol` and
`noise-rust-crypto` for its transit layer, so *SPAKE2 for the code,
Noise for the bytes* is a shipped architecture, not a novel composition.
(magic-wormhole.rs itself is **EUPL-1.2** — evidence we may read, not a
dependency we could take under ADR 0009.)

**The alternatives are worse.** CPace is the CFRG-selected balanced
PAKE, but the Rust [`cpace`](https://crates.io/api/v1/crates/cpace)
crate is **0.1.0 from 2020-05-01, BSD-3-Clause, 2 064 total downloads** —
abandoned. `pakery` (CPace/OPAQUE/SPAKE2/SPAKE2+) surfaced in search and
is **UNVERIFIED**: no download history or review evidence examined.
OPAQUE is an augmented PAKE solving a problem we do not have (there is
no server holding a verifier). SPAKE2 is the only credible Rust option,
and the honest framing is "unaudited but widely deployed for this exact
use", not "reviewed".

### 2.3 Noise, via `snow`

[`snow`](https://crates.io/api/v1/crates/snow) — **0.10.0 (2025-07-19)**,
`Apache-2.0 OR MIT`, **26.3 M total / 3.83 M recent downloads**, repo
[mcginty/snow](https://github.com/mcginty/snow), not archived. Tracks
Noise specification revision 34. Pure-Rust default resolver
(Curve25519, ChaCha20-Poly1305, BLAKE2s/b, SHA-2, AES-GCM) with an
optional `ring` backend; `no_std` with `alloc`. It states **"this
library has not received any formal audit"**.

A thirteen-month-old release is not staleness here: Noise is a frozen
specification and `snow` is its de-facto Rust implementation, at a
download volume two orders of magnitude above the PAKE crate.

**Pattern shapes.** `XX` exchanges both static keys and authenticates
both parties; `KK` requires both statics known in advance; the `pskN`
modifiers mix a pre-shared key in at position N, and with `psk0` every
message including the first is bound to it. That matters twice: it lets
one pattern serve both phases (pairing psk = the PAKE output; session
psk = a secret minted at pairing), and it means a device that is not
paired cannot complete a handshake far enough to learn a paired device's
static identity — default-deny becomes a property of the handshake
rather than a check after it.

### 2.4 rustls with raw public keys — the alternative

rustls is genuinely audited, which SPAKE2 and `snow` are not, and
RFC 7250 raw public keys would remove certificates from a
device-to-device design. Against it: TLS 1.3's external-PSK path is the
awkward route for a PAKE-derived secret and is thinly exercised in
rustls; raw-public-key mutual authentication needs custom verifier
implementations on both sides (the place where a hand-rolled mistake is
silent); and it pulls a substantially larger tree (`aws-lc-rs` or
`ring`) into a `.so` with a 15 MB budget. The audit advantage is real
and is the strongest argument any alternative has in this note.

### 2.5 Where the identity key lives, and why it cannot live in the vault

The vault is plaintext at rest by owner decision
(`spikes/s5-distribution-policy/threat-model.md`, decision 4), which is
survivable for content and **not** survivable for a device identity, for
one specific reason: the vault is a *portable, copyable, third-party-
syncable* artefact. ADR 0008 plans a shared-folder transport over
Dropbox and NAS shares; users take backups. `meta.device_id` living
inside the vault (`store.rs:47-50`) means a copied vault is a **cloned
device identity with a shared `op_seq` space** — the precise fork the
threat model calls out when it says sequence reuse is never legitimate.

So identity must be **device-local, outside the vault**, in the location
the app already uses for device-local state (`%LOCALAPPDATA%\Gilune`,
where the whisper models already sit; Android app-private `filesDir`).

Platform protection for the key bytes:

- **Windows: DPAPI** (`CryptProtectData`, user scope). JNA is already a
  desktop dependency, so this is a small adapter and no new library.
- **Android: Keystore.** Keystore cannot export a raw X25519 private key,
  and hardware X25519 is not broadly available, so the workable shape is
  a Keystore AES-GCM key used to **wrap** the identity file.
- Both are a **capability adapter in Kotlin**, not a Rust platform call —
  ADR 0001's rule, and the same shape as every other OS facility.
- Honest ceiling: DPAPI user scope and a non-auth-bound Keystore key
  protect the file at rest and from other users; **neither protects
  against code running as the user**. `06-sync-and-security.md` asks for
  a "hardware/platform-protected signing identity **where available**",
  and this is what available means here.

## 3. QR, both ends

### 3.1 Render (desktop)

[`qrcode`](https://crates.io/api/v1/crates/qrcode) — **0.14.1
(2024-07-05)**, `MIT OR Apache-2.0`, 19.1 M total downloads, repo
[kennytm/qrcode-rust](https://github.com/kennytm/qrcode-rust). Pure Rust
encoder; the [`image` crate is an optional dependency](https://docs.rs/qrcode/latest/qrcode/),
so the module matrix is reachable with no image stack at all. A
2024 release with no activity since is a maintenance note, not a risk:
QR is a frozen 2006 standard with no security surface on the encode
side.

The cheap shape is therefore **encode in Rust, draw in Compose**: the
pairing secret is minted in the sync crate, so the matrix crosses the
FFI as bits and the shell paints squares on a `Canvas`. **Zero new
Kotlin dependencies**, and the secret never leaves the kernel as a
string the shell might log.

Sizes and coordinates from

## 4. Phone scheduling

- **`PeriodicWorkRequest` floors at 15 minutes**
  (`MIN_PERIODIC_INTERVAL_MILLIS = 900000`); a shorter request is
  silently clamped
  ([define work](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work)).
- `NetworkType.UNMETERED` is the Wi-Fi constraint. `setRequiresCharging`
  would satisfy "be a good citizen" and in practice means *overnight
  only* for most users; `setRequiresBatteryNotLow` costs far less.
- **The 15 minutes is a floor, not a cadence.** Doze batches deferred
  work into maintenance windows that lengthen the longer the device
  stays idle, and App Standby buckets gate it further. The honest
  statement is: near-15-minute cadence while the phone is in use,
  degrading toward hourly or worse in a pocket overnight. Anything that
  needs to be prompt has to be the foreground sync.
- **Android 16 (API 36)**: background jobs started from a foreground
  service must now obey their runtime quotas — this reaches WorkManager
  and `DownloadManager`; user-initiated data-transfer jobs are the
  exempt route.
  **Android 15 (API 35)**: a `dataSync` foreground service is capped at
  6 hours, and `BOOT_COMPLETED` may no longer launch certain FGS types
  ([FGS changes](https://developer.android.com/develop/background-work/services/fgs/changes)).
  Consequence: **routine sync must not be a `dataSync` foreground
  service.** The manifest's own comment already records that there is
  deliberately no boot receiver and no scheduler in it; a periodic
  worker plus foreground sync keeps that posture.

## 5. Quotas, and the shape of a hostile peer

The threat model assigns "per-device quotas and size limits on apply" to
this milestone. Concretely, what a socket exposes that a folder did not:

- **Declared-length allocation.** `sync.rs:432` sizes a buffer from the
  peer's manifest. Streaming chunk-by-chunk into the existing staging
  path (which already hashes incrementally, `capture.rs:112-121`)
  removes both the OOM and the double-copy.
- **Unbounded envelopes.** An operation payload is a document, never
  bytes; a cap in the low megabytes is generous.
- **Unbounded sessions.** Ops-per-session and bytes-per-session caps
  turn "a peer streams forever" into "the session ends and resumes at
  the frontier next time" — which costs nothing, because resumption is
  what frontiers are for.
- **Disk exhaustion.** A declared blob length larger than free space
  should be refused before a byte is written.
- **Handshake flooding.** A PAKE gives one online guess per attempt;
  without an attempt limit, 10⁶ attempts is an afternoon. The code must
  be single-use, short-lived, CSPRNG-generated, and abandoned after a
  small number of failures.

The useful observation is that **every one of these can reuse the
proven halt policy** — raise a visible alert, stop that peer's stream,
apply nothing past the offending point — rather than inventing a second
failure mode. The spike already proved that shape for gaps and corrupt
operations.

## 6. Revocation, and what full replication does to it

Two facts interact and the combination is not obvious.

**Pairing is pairwise, and that is sufficient.** If A pairs with B and A
pairs with C, B never meets C — but B still converges with C's work,
because A is a full replica holding C's operations and serves them on.
Transitive convergence over a pairwise-authenticated overlay is a free
consequence of the owner's full-replica constraint.

**Revocation is therefore also pairwise, and cannot retract history.**
Revoking B on A stops B connecting to A and stops A sending to B. It
does not remove what B already holds — `06-sync-and-security.md` says so
directly ("a lost or malicious device can retain anything it
legitimately decrypted before revocation") — and, in a three-device
mesh, it does not stop B's *already-distributed* operations reaching A
through C.

That last case has a cheap partial answer: refuse to **apply** operations
whose originating `device_id` is locally revoked, whoever delivered them.
It is policy, not cryptography — nothing signs an operation in v0, so a
paired device could still forge history attributed to another device —
but it makes "a revoked device is excluded" a testable property in a
three-replica scenario rather than a two-device coincidence.

The v0 gap to state plainly: **operations are authenticated by the
transport, not individually signed.** That is defensible while every
peer is the same user's own mutually-authenticated device and no relay
exists, and it stops being defensible the moment an untrusted store
holds operations — which is exactly where the crypto ADR and its
external review already sit as a gate. The mechanism that keeps the door
open is storing the **raw received envelope bytes** rather than only the
parsed columns: a full replica must forward a third device's operations
byte-exactly, and any signature added later must verify over the bytes
that were signed.

## 7. The forks, and where the evidence points

1. **Discovery** — mDNS/DNS-SD, not custom broadcast: it is the only
   mechanism Android gives us for free through `NsdManager`, and
   broadcast pays every cost anyway. Split by platform, behind one
   trait: `mdns-sd` in Rust for desktop (and any future headless host,
   which has no JVM), `NsdManager` through a Kotlin adapter on Android
   (no multicast lock, no extra permission, platform-managed battery).
   The failure story is cached-address-first, then manual `host:port`,
   then a diagnostic that names AP isolation. Windows coexistence on
   UDP 5353 is the one thing to measure early.
2. **Pairing** — SPAKE2 over the 6-digit code and over the QR's longer
   secret, one exchange, then Noise `XXpsk0` with the PAKE output as
   the pre-shared key to exchange and bind the static identities.
   `spake2` is unaudited; it is also what magic-wormhole ships for this
   exact job, and the alternatives are abandoned or unverified.
3. **Transport** — `snow`. Also unaudited, but 26 M downloads against a
   frozen specification, dual-licensed, no async runtime, `no_std`-capable.
   rustls with raw public keys is the serious rival and its audit is a
   real advantage; it loses on PSK fit, on hand-written verifiers, and
   on tree size against a 15 MB budget.
4. **Identity storage** — device-local, outside the vault, wrapped by a
   DPAPI/Keystore capability adapter. This is not a preference: an
   identity inside a copyable vault is a cloned sequence space, and
   putting it outside makes the owner's re-enrolment rule a mechanical
   consequence of storage placement rather than a policy check someone
   has to remember to run.
5. **QR** — encode with the Rust `qrcode` crate and paint the matrix in
   Compose (no new Kotlin dependency); scan with CameraX plus ZXing
   `core` (Apache-2.0, no Play services), asking for `CAMERA` only when
   the user taps Scan, and keeping the 6-digit path always available so
   the camera is never required to sync.
6. **Placement** — apply belongs in `gilune-kernel` (it writes heads,
   tombstones and idempotency — kernel invariants); discovery, pairing,
   session and framing belong in a new `gilune-sync` crate behind a
   `Transport` trait, which is what lets the entire S4 scenario suite
   run over a loopback socket before any radio is involved.
7. **Scheduling** — foreground sync on resume; `PeriodicWorkRequest`
   at 15 minutes with `UNMETERED` and `batteryNotLow`, no charging
   requirement, no `dataSync` foreground service. State the real
   cadence honestly: 15 minutes is a floor that Doze will stretch.
